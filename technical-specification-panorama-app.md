# Техническое задание: веб-приложение для интерактивных панорам объектов

## 1. Цель проекта {#1-цель-проекта}

Разработать веб-приложение, в котором администратор загружает панорамные
изображения помещений, размещает на них интерактивные графические
элементы и публикует объект по защищённой ссылке с QR-кодом.

Пользователь сканирует QR-код камерой телефона и открывает мобильную
страницу объекта. На странице он может просматривать панорамы помещений,
вращать изображение, менять масштаб и взаимодействовать с добавленными
администратором выносками.

Проект --- MVP с понятной архитектурой, без избыточной сложности.
Приоритеты: безопасность доступа, удобная мобильная версия, корректная
работа с панорамами и простота дальнейшего расширения.

## 2. Технологический стек {#2-технологический-стек}

### Frontend

-   React
-   TypeScript
-   Vite
-   Tailwind CSS
-   shadcn/ui
-   Lucide React или другой согласованный набор готовых SVG-иконок
-   React Router
-   TanStack Query для серверного состояния
-   React Hook Form + Zod для форм и валидации
-   Библиотека просмотра 360°-панорам: выбрать и зафиксировать одну
    библиотеку после проверки совместимости с React и мобильными
    браузерами (предпочтительно Marzipano или Pannellum).

### Backend

-   Laravel
-   PHP --- версия, совместимая с выбранной стабильной версией Laravel
-   REST API
-   Laravel Sanctum для авторизации административной части
-   Валидация входных данных средствами Laravel Form Request
-   Хранение загруженных файлов в Laravel Storage через абстракцию
    дисков

### Инфраструктура разработки

Один `docker-compose.yml`, содержащий:

1.  `frontend` --- React + Vite, dev server.
2.  `backend` --- Laravel + PHP runtime.
3.  `webserver` --- Nginx для Laravel API и статических/загружаемых
    ресурсов, если выбранная схема требует отдельного веб-сервера.
4.  `mysql` --- MySQL.
5.  `phpmyadmin` --- веб-интерфейс администрирования MySQL.

Если для корректной работы Laravel необходим отдельный контейнер Nginx,
он должен быть частью того же Compose-проекта. Не создавать отдельные
Compose-файлы для каждого сервиса.

Для локальной разработки обеспечить hot reload frontend и удобную работу
с Laravel. Версии образов и сервисов фиксировать, не использовать
`latest`.

## 3. Основные пользовательские сценарии {#3-основные-пользовательские-сценарии}

### 3.1. Администратор {#31-администратор}

1.  Открывает `/admin`.
2.  Авторизуется.
3.  Создаёт объект: задаёт название и при необходимости описание.
4.  Добавляет в объект одну или несколько панорам.
5.  Для каждой панорамы задаёт название, например: «Коридор»,
    «Гостиная», «Кухня».
6.  Загружает панорамное изображение.
7.  Открывает редактор панорамы.
8.  Добавляет графические элементы: текстовые плашки, размеры, выноски,
    маркеры и другие поддерживаемые типы.
9.  Перемещает элементы по панораме, редактирует их свойства и удаляет
    ненужные.
10. Сохраняет панораму как черновик.
11. Предварительно просматривает результат в режиме, максимально близком
    к пользовательскому.
12. Публикует объект.
13. Система генерирует защищённый публичный токен и URL.
14. Администратор видит QR-код и может скачать его или скопировать
    ссылку.

### 3.2. Посетитель {#32-посетитель}

1.  Сканирует QR-код.
2.  Открывает публичную ссылку вида `/view/{publicToken}`.
3.  Система проверяет токен и статус публикации объекта.
4.  При успешной проверке отображается объект и первая доступная
    панорама.
5.  Посетитель вращает панораму, приближает и отдаляет изображение.
6.  Посетитель взаимодействует с выносками и маркерами.
7.  Если у объекта несколько панорам, переключается между ними через
    компактный селектор помещений или стрелки.

Посетитель не должен иметь возможности получить доступ к объекту простым
перебором числового ID.

## 4. Маршруты приложения {#4-маршруты-приложения}

### Frontend routes

-   `/admin/login` --- вход администратора.
-   `/admin` --- главная панель.
-   `/admin/objects` --- список объектов.
-   `/admin/objects/new` --- создание объекта.
-   `/admin/objects/:id` --- просмотр и редактирование объекта.
-   `/admin/objects/:id/panoramas/:panoramaId` --- редактор панорамы.
-   `/view/:publicToken` --- публичная страница объекта.

Можно скорректировать структуру маршрутов, если это улучшит архитектуру,
но административные и публичные маршруты должны быть логически
разделены.

### Backend API

Примерная структура:

-   `POST /api/admin/login`
-   `POST /api/admin/logout`
-   `GET /api/admin/me`
-   `GET /api/admin/objects`
-   `POST /api/admin/objects`
-   `GET /api/admin/objects/{id}`
-   `PATCH /api/admin/objects/{id}`
-   `DELETE /api/admin/objects/{id}`
-   `POST /api/admin/objects/{id}/publish`
-   `POST /api/admin/objects/{id}/regenerate-token`
-   `GET /api/admin/objects/{id}/qr`
-   CRUD для панорам объекта.
-   CRUD для аннотаций панорамы.
-   `GET /api/public/objects/{publicToken}` --- получение
    опубликованного объекта по токену.

Это ориентировочный контракт. Перед реализацией оформить API-контракт и
согласовать структуру DTO/Resources. Не отдавать публичному API
внутренние поля и административные данные.

## 5. Модель данных {#5-модель-данных}

Предлагаемая базовая схема. Названия таблиц и полей можно адаптировать к
соглашениям Laravel.

### `users`

Администраторы приложения.

-   `id`
-   `name`
-   `email` --- unique
-   `password`
-   `created_at`
-   `updated_at`

На первом этапе достаточно одной роли администратора. Не строить сложную
RBAC-систему без необходимости.

### `objects`

Объекты, доступные для просмотра.

-   `id`
-   `title`
-   `description` --- nullable
-   `status` --- `draft` / `published` / `archived`
-   `public_token_hash` --- nullable, unique
-   `published_at` --- nullable
-   `created_at`
-   `updated_at`

`public_token_hash` --- хеш публичного токена. Сам токен хранится у
администратора только в момент генерации/показа ссылки и не должен
сохраняться в открытом виде в БД.

### `panoramas`

Панорамы, принадлежащие объекту.

-   `id`
-   `object_id` --- foreign key
-   `title`
-   `image_path`
-   `image_mime_type`
-   `image_size`
-   `width`
-   `height`
-   `sort_order`
-   `status` --- `draft` / `ready`
-   `created_at`
-   `updated_at`

### `annotations`

Графические элементы, привязанные к панораме.

-   `id`
-   `panorama_id` --- foreign key
-   `type` --- тип элемента, например `label`, `measurement`, `callout`,
    `marker`
-   `template_key` --- ключ шаблона оформления
-   `position` --- JSON с координатами и параметрами размещения
-   `content` --- JSON с содержимым элемента
-   `style` --- JSON с разрешёнными параметрами внешнего вида
-   `sort_order`
-   `created_at`
-   `updated_at`

Структуру JSON документировать и валидировать. Не сохранять произвольный
исполняемый HTML/CSS/JavaScript, введённый администратором.

### Дополнительные таблицы

Добавлять только при реальной необходимости. Например, таблицу истории

## 6. Защита публичного доступа {#6-защита-публичного-доступа}

Это обязательная часть проекта.

1.  Не использовать числовой ID объекта как средство доступа.
2.  Генерировать криптографически стойкий случайный токен достаточной
    длины (например, не менее 32 случайных байт в URL-safe
    представлении).
3.  В базе хранить только хеш токена. Для проверки входящего токена
    вычислять хеш и сравнивать с сохранённым значением.
4.  Публичный URL должен выглядеть примерно так: `/view/{publicToken}`.
    Не использовать предсказуемые значения вроде `6262718`.
5.  Параметр `?secret=sol` не использовать: короткий секрет легко
    угадать, а query-параметры чаще попадают в логи, историю браузера и
    аналитические системы.
6.  Публичный API должен возвращать данные только для опубликованного
    объекта с валидным токеном.
7.  Черновики не должны быть доступны через публичный API.
8.  Предусмотреть ограничение частоты запросов к публичному endpoint.
9.  Не раскрывать существование объекта при невалидном токене:
    возвращать одинаковый ответ `404`.
10. При повторной генерации токена старый токен должен немедленно
    переставать работать.
11. Не помещать токен в логи приложения, аналитику или сообщения об
    ошибках.
12. Для административных API использовать авторизацию, CSRF-защиту в
    соответствии со схемой Sanctum, проверку прав и валидацию входных
    данных.
13. Настроить безопасную загрузку файлов: проверять MIME-тип,
    расширение, размер, фактическое содержимое и допустимые форматы. Не
    доверять имени файла от клиента.
14. Загружаемые файлы не должны исполняться сервером.

QR-код содержит полный публичный URL. QR-код --- только удобный способ
передать ссылку, а не отдельный механизм авторизации.

## 7. Работа с панорамами {#7-работа-с-панорамами}

### Формат

На первом этапе поддерживать equirectangular 360°-изображения. Типичный
формат --- 2:1 по соотношению ширины к высоте.

При загрузке:

-   Проверять формат и допустимый размер файла.
-   Проверять разрешение изображения.
-   Сохранять оригинал.
-   При необходимости предусмотреть создание оптимизированной
    версии/тайлов для больших изображений.
-   Не загружать панораму целиком в административный список объектов.

### Просмотр

Пользовательская панорама должна поддерживать:

-   вращение мышью на desktop;
-   вращение касанием на мобильных устройствах;
-   zoom in / zoom out;
-   управление жестами pinch-to-zoom;
-   полноэкранный режим, если поддерживается браузером;
-   адаптивное отображение на мобильных экранах.

Не реализовывать собственный 360°-движок, если выбранная библиотека уже
решает эту задачу.

## 8. Редактор панорам и аннотаций {#8-редактор-панорам-и-аннотаций}

Редактор --- ключевая часть административной панели.

### Основной интерфейс

-   Центральная область --- интерактивная панорама.
-   Панель инструментов --- типы доступных элементов.
-   Боковая панель или popover --- свойства выбранного элемента.
-   Список элементов текущей панорамы.
-   Кнопки сохранения, отмены и предпросмотра.

### Типы элементов для MVP

1.  **Текстовая плашка** --- короткий текст, например «Высота 3 м».
2.  **Размер/измерение** --- значение и единица измерения, например
    `3 м`.
3.  **Выноска** --- маркер и связанный с ним текстовый блок.
4.  **Маркер** --- точка на панораме с открываемой информацией.

Для каждого элемента предусмотреть:

-   добавление;
-   выбор;
-   перемещение;
-   редактирование содержимого;
-   изменение разрешённых параметров стиля;
-   удаление;
-   изменение порядка отображения.

### Координаты

Координаты аннотаций должны быть привязаны к системе координат панорамы,
а не к размеру DOM-контейнера. Для 360°-панорам предпочтительно хранить
yaw/pitch либо координаты, которые выбранная библиотека стабильно
преобразует в углы обзора.

Не хранить только пиксельные координаты относительно текущего viewport:
при изменении размера экрана и масштаба элементы будут смещаться.

Зафиксировать единую модель координат и использовать её и в редакторе, и
в публичном просмотрщике.

### Шаблоны оформления

Шаблоны должны быть конфигурационными, а не отдельными вручную
реализованными компонентами для каждого объекта.

Создать централизованный каталог шаблонов, например:

-   `simple-label`
-   `measurement`
-   `callout`
-   `marker`

Для шаблона определить:

-   уникальный ключ;
-   название для интерфейса;
-   тип элемента;
-   доступные поля;
-   допустимые настройки оформления;
-   компонент отображения.

Не позволять данным из БД произвольно загружать компоненты или исполнять
код. Рендеринг должен происходить только через заранее
зарегистрированные компоненты.

## 9. Интерфейс публичной страницы {#9-интерфейс-публичной-страницы}

Mobile-first. Основной сценарий --- открытие QR-кода с телефона.

### Состав страницы

-   Панорама занимает основную доступную область экрана.
-   Название текущего помещения.
-   Компактный переключатель помещений.
-   Кнопки или жесты управления масштабом.
-   Интерактивные аннотации поверх панорамы.
-   При необходимости --- название объекта.

### Переключение помещений

Если панорама одна --- селектор помещений можно скрыть.

Если панорам несколько:

-   показывать название текущей комнаты;
-   открывать список помещений через dropdown/bottom sheet;
-   дополнительно можно предусмотреть стрелки «предыдущее/следующее»;
-   сохранять корректное состояние при переключении.

### UX

-   Не перегружать экран элементами управления.
-   Учитывать safe areas мобильных устройств.
-   Предусмотреть состояния загрузки и ошибки.
-   Если токен невалиден или объект снят с публикации --- показывать
    нейтральную страницу «Объект не найден или больше недоступен».
-   Если изображение не загрузилось --- показать понятное сообщение и
    возможность повторить загрузку.

### Главная

-   Название и описание.
-   Список панорам.
-   Добавление и удаление панорам.
-   Изменение порядка панорам.
-   Статус объекта.
-   Публичная ссылка.

-   Генерация нового токена с подтверждением.

### Страница панорамы

-   Загрузка/замена изображения.
-   Название помещения.
-   Открытие редактора.
-   Предпросмотр.
-   Сохранение черновика.

### Авторизация

-   Страница входа.
-   Защита всех `/admin/*` маршрутов.
-   Сессия/токен авторизации с безопасным хранением.
-   Кнопка выхода.
-   Не добавлять публичную регистрацию.

## 11. Архитектура и организация кода {#11-архитектура-и-организация-кода}

Применять принципы:

-   Clean Architecture --- в разумном объёме, без искусственного
    усложнения.
-   SOLID --- там, где это повышает поддерживаемость.
-   DRY --- общая логика и UI не дублируются.
-   KISS --- не вводить абстракции без конкретной пользы.
-   FAD --- придерживаться feature-oriented структуры, группируя код по
    функциональным областям.

Не превращать MVP в набор избыточных слоёв и интерфейсов. Архитектура
должна оставаться понятной небольшому проекту.

### Frontend: рекомендуемая структура

``` text
frontend/
  src/
    app/
      router/
      providers/
      config/
    pages/
      admin/
      public-view/
    features/
      auth/
      objects/
      panoramas/
      annotations/
      publishing/
    entities/
      object/
      panorama/
      annotation/
    shared/
      api/
      components/
      hooks/
      lib/
      types/
      config/
      styles/
```

Границы модулей соблюдать последовательно. Не создавать пустые слои «на
будущее».

### Backend: рекомендуемая структура

``` text
backend/
  app/
    Http/
      Controllers/
        Api/
          Admin/
          Public/
      Requests/
      Resources/
    Models/
    Actions/
    Services/
    Policies/
    Enums/
  routes/
    api.php
  config/
  database/
    migrations/
    seeders/
  tests/
```

Контроллеры должны быть тонкими: принять запрос, вызвать прикладную
операцию, вернуть Resource/ответ. Бизнес-правила не размещать в
контроллерах и React-компонентах.

### Конфигурация

В конфигурацию выносить действительно изменяемые параметры:

-   лимиты загрузки;
-   допустимые MIME-типы и расширения;
-   лимиты размеров и разрешений панорам;
-   настройки публичных URL;
-   настройки viewer;
-   каталог типов аннотаций и шаблонов;
-   UI-настройки, которые могут меняться централизованно.

Не выносить каждую строку и каждое очевидное значение в отдельный
конфиг. Не создавать универсальный конфиг-фреймворк.

## 12. UI и дизайн-система {#12-ui-и-дизайн-система}

-   Использовать shadcn/ui и Tailwind CSS.
-   Иконки --- готовые SVG через согласованную библиотеку,
    предпочтительно Lucide.
-   Не использовать emoji в интерфейсе.
-   Не рисовать иконки символами Unicode.
-   Повторяющиеся UI-элементы оформлять переиспользуемыми компонентами.
-   Использовать единые design tokens: цвета, отступы, радиусы,
    типографику, тени.
-   Поддерживать адаптивность административной панели, но приоритет
    публичной страницы --- мобильные устройства.
-   Не создавать собственные компоненты там, где подходит shadcn/ui.

## 13. Docker Compose {#13-docker-compose}

Создать корневую структуру:

``` text
project/
  docker-compose.yml
  .env.example
  frontend/
    Dockerfile
    ...
  backend/
    Dockerfile
    ...
  docker/
    nginx/
      default.conf
  README.md
```

### Требования

-   Все сервисы запускаются одной командой `docker compose up`.
-   Данные MySQL хранятся в named volume.
-   Загруженные панорамы хранятся в volume или в локальном storage
    backend-контейнера с постоянным volume.
-   Не хранить секреты в репозитории.
-   Добавить `.env.example` с описанием всех переменных.
-   Добавить healthcheck для MySQL и зависимость backend от готовности
    БД.
-   Настроить корректные внутренние адреса сервисов через Docker
    network.
-   Frontend в dev-режиме должен обращаться к backend через настроенный
    Vite proxy или корректный API base URL.
-   phpMyAdmin доступен только в локальной среде разработки.
-   Не публиковать MySQL наружу без необходимости.
-   Не использовать `container_name`, если он мешает масштабированию или
    повторному запуску проектов.
-   Настроить volumes так, чтобы bind mount исходников не затирал
    установленные внутри контейнера зависимости.

Пример локальных адресов:

-   Frontend: `http://localhost:5173`
-   Backend API: `http://localhost:8000` или через Nginx на выбранном
    порту
-   phpMyAdmin: `http://localhost:8081`

Финальные порты и схема маршрутизации должны быть единообразны и
задокументированы.

## 14. Нефункциональные требования {#14-нефункциональные-требования}

-   TypeScript `strict` включён.
-   Не использовать `any` без обоснованной необходимости.
-   Единый формат API-ответов и ошибок.
-   Серверная валидация обязательна, клиентская --- для UX.
-   Обрабатывать ошибки загрузки и сетевые ошибки.
-   Не загружать все изображения и все панорамы заранее без
    необходимости.
-   Использовать lazy loading для панорам, которые не открыты.
-   Следить за размером изображений и производительностью мобильных
    устройств.
-   Добавить базовые тесты критичной логики.
-   Добавить ESLint и форматирование кода.
-   Не оставлять фиктивные кнопки, заглушки и неработающие действия в
    реализованных сценариях.

## 15. Тестирование и критерии готовности {#15-тестирование-и-критерии-готовности}

### Безопасность

-   Нельзя открыть объект по его числовому ID.
-   Невалидный токен возвращает `404`.
-   Черновой объект недоступен публично.
-   Смена токена делает старую ссылку недействительной.
-   Административные API недоступны без авторизации.
-   Загрузка неподдерживаемого файла отклоняется.

### Администрирование

-   Администратор может войти и выйти.
-   Может создать, изменить и удалить объект.
-   Может добавить несколько панорам.
-   Может менять порядок панорам.
-   Может создавать, редактировать, перемещать и удалять аннотации.
-   Может сохранить черновик и опубликовать объект.
-   Может получить QR-код и публичную ссылку.

### Публичная часть

-   Ссылка из QR-кода открывает правильный объект.
-   Панорама корректно отображается на мобильном устройстве.
-   Работают вращение и масштабирование.
-   Аннотации остаются привязаны к правильным местам при вращении и
    изменении масштаба.
-   Переключение помещений работает для объектов с несколькими
    панорамами.
-   Неопубликованный или недоступный объект не раскрывает свои данные.

### Docker

-   Чистый запуск по инструкции работает.
-   Миграции выполняются.
-   Данные БД и загруженные изображения сохраняются после перезапуска
    контейнеров.

## 16. Порядок реализации {#16-порядок-реализации}

Не генерировать весь проект одним большим коммитом. Работать итерациями,
после каждой проверять запуск и работоспособность.

### Этап 1. Основа проекта {#этап-1-основа-проекта}

-   Создать структуру репозитория.
-   Подготовить Docker Compose.
-   Поднять Laravel, React/Vite и MySQL.
-   Настроить shadcn/ui, Tailwind, TypeScript.
-   Подготовить `.env.example` и README.
-   Проверить запуск всех сервисов.

### Этап 2. Backend и безопасность {#этап-2-backend-и-безопасность}

-   Создать модели, миграции и связи.
-   Настроить административную авторизацию.
-   Реализовать CRUD объектов и панорам.
-   Реализовать генерацию, хеширование и проверку публичного токена.
-   Реализовать публикацию и снятие с публикации.
-   Реализовать публичный endpoint.

### Этап 3. Админка {#этап-3-админка}

-   Реализовать вход.
-   Реализовать список и карточку объектов.
-   Реализовать управление панорамами.
-   Реализовать загрузку изображений.
-   Реализовать генерацию QR-кода и публичной ссылки.

### Этап 4. Просмотрщик панорам {#этап-4-просмотрщик-панорам}

-   Интегрировать выбранную 360°-библиотеку.
-   Реализовать вращение и zoom.
-   Реализовать мобильное управление.
-   Реализовать переключение комнат.

### Этап 5. Редактор аннотаций {#этап-5-редактор-аннотаций}

-   Зафиксировать модель координат.
-   Реализовать добавление, перемещение и удаление элементов.
-   Реализовать шаблоны.
-   Реализовать редактирование содержимого и стилей.
-   Обеспечить одинаковое отображение аннотаций в редакторе и публичной
    части.

### Этап 6. Проверка и документация {#этап-6-проверка-и-документация}

-   Пройти критерии готовности.
-   Добавить тесты критичных сценариев.
-   Проверить мобильную версию.
-   Обновить README с командами запуска, миграций, создания
    администратора и резервного копирования данных.

## 17. Правила работы AI-агента {#17-правила-работы-ai-агента}

Перед началом реализации:

1.  Изучи существующую структуру репозитория. Если проект пустой ---
    создай структуру из этого ТЗ.
2.  Кратко предложи архитектуру и перечисли ключевые технические
    решения.
3.  Укажи выбранную библиотеку панорам и объясни выбор.
4.  Покажи итоговую структуру Docker Compose и сетевую схему.
5.  Зафиксируй API-контракт и модель координат аннотаций.

Во время реализации:

-   Выполняй работу по этапам, не перескакивай через фундаментальные
    части.
-   Не переписывай уже работающий код без причины.
-   Не добавляй библиотеки без необходимости.
-   Не дублируй бизнес-логику.
-   Не оставляй TODO вместо реализации обязательной функциональности.
-   Не используй фиктивные данные в production-сценариях.
-   Не ослабляй безопасность ради упрощения.
-   После каждого этапа запускай доступные проверки и исправляй ошибки.
-   Если обнаружено противоречие в требованиях или важное архитектурное
    решение не определено, сначала задай конкретный вопрос, а не
    принимай рискованное предположение.

## 18. Что не входит в MVP {#18-что-не-входит-в-mvp}

Не реализовывать без отдельного согласования:

-   регистрацию посетителей;
-   пользовательские аккаунты и личные кабинеты;
-   оплату и подписки;
-   совместное редактирование в реальном времени;
-   сложную систему ролей и разрешений;
-   комментарии и чат;
-   видеопанорамы;
-   полноценный 3D-редактор;
-   аналитику поведения посетителей;
-   мультиязычность, если она не потребуется на первом этапе.

## 19. Итоговый результат {#19-итоговый-результат}

В результате должен получиться локально запускаемый проект с одним
Docker Compose, в котором:

-   администратор авторизуется в `/admin`;
-   создаёт объект и загружает одну или несколько 360°-панорам;
-   размещает на панорамах графические аннотации через визуальный
    редактор;
-   сохраняет черновик и публикует объект;
-   получает случайную защищённую ссылку и QR-код;
-   посетитель открывает ссылку с телефона и просматривает панорамы с
    интерактивными элементами;
-   данные, изображения и настройки сохраняются между перезапусками
    контейнеров.

Деплой на production выполняется владельцем проекта отдельно. В рамках
этой задачи подготовить конфигурацию и документацию для последующего
самостоятельного деплоя.
